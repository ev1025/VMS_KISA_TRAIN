# 실험 방법론 (KISA 4항목: 방화·침입·배회·쓰러짐)

**이 문서는 "어떻게 실험하는가"만 적는다.** 성능 수치는 적지 않는다(금방 낡는다).

- 실험별 채점 결과 → `results/<실험명>/score.txt`
- 모델 계보(무슨 데이터로 학습했나) → `results/MODELS.json`
- 비교 보기 → 대시보드(8890) 결과 탭
- 무슨 숫자로 합격을 판단하는가 → `docs/kisa/B200_평가.md`

## 0. 실행 규약

### 유일 진입점 = `scripts/exp_queue.py`

```
python scripts/exp_queue.py run configs/<queue>.yaml --jobs 2 [--wait-tmux <세션>] [--rebuild-human]
python scripts/exp_queue.py status configs/<queue>.yaml
```

- 실험 추가 = yaml 에 한 항목. **실행 중인 .sh/.yaml 을 편집해 붙이지 않는다**(바이트 오프셋이 깨져 고아 프로세스가 생긴다).
- 산출: `runs/<exp>/<model>/weights/best.pt` · `results/<exp>/{meta.json,score.txt}` · `logs/queue/<exp>.log`
- 재실행 안전: `best.pt` 가 있으면 학습을 건너뛰고, `score.txt` 가 있으면 그 실험 전체를 건너뛴다. `_exp/` 는 잡별 임시 목록·캐시라 지워도 된다.

### 러너가 강제하는 값 (yaml `defaults` 로 조절)

### 이미지 소스 — 학습 해상도에 따라 자동으로 갈린다

디코딩이 병목이라 긴 변 960 으로 줄인 사본(`/NHNHOME/vms_r960`)을 먼저 쓴다
(실측 8워커: 원본 1920 = 261장/초, 960 사본 = 727장/초).

**단 960 사본은 요구 해상도가 960 이하일 때만 쓴다.** `find_dataset()` 이
`imgsz × (1 + multi_scale)` 로 판단해 넘으면 원본으로 간다.

| imgsz | multi_scale 0.5 상한 | 읽는 곳 |
|---|---|---|
| 640 | 960 | 960 사본 (무손실) |
| 960 | 1,440 | 원본 |
| 1280 | 1,920 | 원본 |

2026-09-15 이전에는 이 게이트가 없어 **imgsz 960·1280 실험이 960 사본을 확대해 학습**했다.
해상도 그리드서치가 성립하지 않아 해당 실험(`s2_s960` `s2_m960` `s2_s1280`
`person_coco_kisa_s960`)을 폐기하고 다시 돌렸다. 폐기본은 `_invalid_r960_20260915/`.

실제로 어디서 읽었는지는 `_exp/<실험>/source.json` 과 `results/<실험>/meta.json` 의
`source` 에 남는다. 고해상도 실험 결과가 이상하면 여기부터 본다.

### GPU 사용

- 사용 전 `nvidia-smi` 로 타 사용자 점유를 확인하고 **본인 프로세스만** 종료한다.

에폭 시간이 갑자기 3~4배로 늘면 캐시·워커 설정과 동시 잡 수를 먼저 의심한다.

## 1. 실험 축

각 축은 **무엇을 바꾸는가 · 어디서 바꾸는가 · 주의할 점**만 적는다.

### A. 입력 해상도 (imgsz)

- 바꾸는 곳: yaml `train.imgsz` (640 / 960 / 1280). 배치 크기를 같이 내려야 VRAM 이 맞는다.
- **학습 imgsz 와 채점 imgsz 를 반드시 같게** 둔다. 다르면 소형 불꽃 리콜이 무너진다.
- 해상도를 올리면 에폭 시간이 제곱으로 늘어난다. 1280 은 640 대비 약 4배.

### B. 모델 백본

- 바꾸는 곳: yaml `model` (yolo11n/s/m/l/x, yolo26n, yolov8 계열). 가중치는 `model/pretrained/`.
- 별도 계열: `scripts/rtdetr_train.py`(RT-DETR), `scripts/world_smoke.py`(YOLO-World 교사 스모크 테스트).
- 큰 모델은 batch 를 내려야 한다(11x 는 batch 64 이하). 에폭 시간이 2~3배가 되니 큐 뒤쪽에 둔다.

### C. 데이터 조합

- 바꾸는 곳: yaml `base`(베이스 풀) + `extras`(추가 세트 이름 목록). 세트 정의는 `docs/data.md`.
- 규칙 두 가지는 `data.md` 에 있다. 음성(배경) 비율 10% 이내, 채점셋은 절대 금지.
- 도메인이 다른 공개셋(FASDD 등)은 mAP 는 올리지만 KISA 채점은 그대로인 경우가 많다. 넣었으면 반드시 채점까지 보고 판단한다.

### D. 오버샘플 배수

- 바꾸는 곳: yaml `oversample: { human_fire: 5 }` → 러너가 train.txt 에 그만큼 반복해 적는다.
- 배수를 올리면 학습 장수가 그대로 늘어 에폭 시간도 늘어난다. 너무 키우면 그 세트에 과적합된다.

### E. 베이스 데이터 양

- 바꾸는 곳: yaml `base` 교체(예: 48k 평면풀 ↔ 24k 프록시) 또는 비율 스윕 `scripts/fire_matrix2.py ratio`.
- 원천이 30fps 연속 프레임이라 장수를 늘려도 정보량이 비례해 늘지 않는다. 포화 지점을 확인하고 쓴다.

### F. 의사라벨 (pseudo-label)

- 구현: `scripts/pl_*.py`. 교사 모델 → 타일 추론 → NMS → `--keep-conf` 이상만 채택.
- `--empty-conf`~`--keep-conf` 사이 애매한 박스가 걸린 프레임은 버린다(미탐이 negative 로 굳는 것을 막는다).
- 샘플링은 `--sample-s`(초 간격) · `--cap`(영상당 장수).
- **평가에 쓰지 않는다.** 교사 지식의 복사이고 교사의 오탐도 정답으로 굳는다. 야간처럼 교사가 약한 조건에서는 오탐이 절반까지 나온다.

### G. 하드네거티브

- 구현: `scripts/build_hardsets.py` → `data/학습데이터/_hard/*.txt` 목록을 extras 로 넣는다.
- 오검을 줄이는 대신 미검이 늘어나는 교환이 반복된다. 넣을 때는 정검·미검·오검을 같이 본다.

### H. 크롭 학습

- 구현: `scripts/make_crops.py`. 발화점 후보를 **깜빡임(연속 프레임 표준편차)** 으로 찾아 512px 크롭.
- 근거: 불은 흔들리고 주차 차량·건물 조명은 안 흔들린다.
- 지금은 손라벨 작업용 크롭 생성에만 쓴다. 크롭 이미지로 학습하는 축은 아직 안 해봤다.

### I. 추론 타일

- 구현: `score_kisa.py --tiles`, `scripts/*_tilescan.py`. 프레임을 3x3 으로 잘라 각각 960 으로 추론 후 좌표 합성.
- 원거리 소형 객체에 효과가 크다. 비용은 프레임당 9회 추론.
- 항목마다 유불리가 다르다. 타일 덤프와 기존 덤프를 둘 다 채점해 비교한다.

### J. 초해상 (SR)

- 구현: `scripts/sr_test.py`, `sr_fp.py` (Real-ESRGAN ×2 → 1280 추론), 가중치 `model/sr/`.
- 리콜과 오탐이 같이 올라간다. 채택하려면 **오탐 검증(`sr_fp.py`)까지** 통과해야 한다.

### K. 도메인 적응 (FDA)

- 구현: `scripts/fda_build.py`, `fda_x_train.sh`. 소스의 저주파 스펙트럼을 타깃 도메인으로 치환.

### L. 시퀀스·트랙 판정 (방화 외 3항목)

| 접근 | 구현 |
|---|---|
| 프레임 독립 판정 | `score_kisa.py` 규칙 |
| 트랙별 독립 판정 | `scripts/fall_track.py` (키포인트 → 트랙 → 59차원 피처 → SeqNet) |
| 시퀀스 분류기 | `fall_seq_train.py`, `seq_train.py` |
| 골격 시공간 그래프 | `posec3d_*.py` |
| 트래커 선택 | ByteTrack(기존 덤프) vs 자체 트래커(타일 덤프) |

여러 사람의 신호를 한 벡터로 섞으면 희석된다. **사람별로 따로 판정하고 가장 이른 시각을 쓴다.**

### M. 판정 규칙 (학습과 무관한 후처리)

- 방화: `f<conf> <n>/<m>` = conf 임계 + m프레임 중 n프레임. 연기 가중치 옵션.
- 침입·배회: conf · 연속 조건 · hold · settle · gap + **"다수면 마지막 사람"** 트랙 규칙.
- 쓰러짐: 트랙별 임계 `th` · `need`.
- 규칙 변경이 모델 교체보다 점수를 크게 움직인 적이 많다. 모델을 바꾸기 전에 규칙 스윕을 먼저 돌린다.
- 스윕 최고값은 10편 과적합이라 **성적으로 보고하지 않는다**(`docs/kisa/B200_평가.md`).

### N. 하이퍼파라미터 최적화

- 구현: `model.py tune --model <m> --imgsz <n>` (Optuna) → `configs/tune_best_*.yaml` → `model.py train --hp <yaml>`.
- 도메인 기본 레시피는 `model.py` 의 `RECIPE`: `flipud=0`(불꽃 상하반전 금지) · `hsv_s=0.5, hsv_v=0.4`(색왜곡 약하게) · `mosaic=1.0, close_mosaic=10` · `cos_lr=True` · `patience=30`.

### O. 교차검증·홀드아웃

| 방식 | 구현 |
|---|---|
| FASDD 5-fold | `scripts/fasdd_kfold.py` |
| 방화 k-fold | `scripts/fire_kfold.py` |
| 장소 홀드아웃(LOO) | `scripts/fire_matrix2.py loo` |

클립·장소 단위로 나눈다. 프레임 단위로 나누면 같은 장면이 양쪽에 들어가 누수가 된다.

## 2. 채점 규칙 두 벌 (구 규칙 / 신규칙)

- 같은 가중치라도 규칙에 따라 점수가 크게 달라지므로, `score_kisa.py` 는 두 규칙을 모두 출력한다.
- 실험끼리 비교할 때는 **같은 규칙끼리** 비교한다. 서로 다른 규칙의 최고값을 나란히 놓지 않는다.

## 3. 그리드 짜는 법

```
베이스     <풀 이름>
모델       yolo11n | 11s | 11m
해상도     640 | 960 | 1280
손라벨배수  x5 | x10
추가셋     없음 | <세트> | <세트 조합>
에폭       40(스크리닝) → 80(확정)
```

- 축을 한 번에 여러 개 바꾸지 않는다. 바꾼 축이 둘이면 원인을 못 가른다.
- 1단계는 40에폭 스크리닝으로 후보를 좁히고, 살아남은 것만 80에폭으로 확정한다.
- 실행 전에 조합 수 × 잡당 시간 ÷ 동시 잡 수로 총 소요를 계산한다. 이틀을 넘기면 축을 줄인다.
- 같은 이름의 실험이 `results/` 에 있으면 러너가 건너뛴다. 재실행하려면 그 폴더를 지운다.

## 4. 판정 규칙을 찾는 법

학습은 오래 걸리고 규칙은 공짜다. **모델을 바꾸기 전에 규칙을 먼저 훑는다.**
2026-09-15 에 쓰러짐 90.00 -> 100.00, 방화 77.78 -> 88.89 이 전부 규칙에서 나왔다.

### 4.1 추론은 한 번만 한다

조합마다 추론을 다시 돌리면 몇 시간이 몇 십 시간이 된다. 신뢰도·확률을 **한 번만 덤프**해 두고
규칙은 파일만 읽어 훑는다.

| 항목 | 덤프 위치 | 한 줄에 담기는 것 |
|---|---|---|
| 방화 | `dumps/score_tl/<실험>.json` | `[t, 불max, 연기max]` + gt |
| 쓰러짐 | `dumps/fall_seq_<해상도>/<편>.json` | 트랙별 `(창끝 시각, 로짓)` |

**요령: 문턱을 절대 못 넘는 값(예 1.1)으로 두고 돌린다.** 판정기는 첫 발화에서 멈추므로
그냥 돌리면 그 뒤 구간이 안 남는다. 발화를 막으면 영상 끝까지 쌓인다.

도구: `scripts/fall_sweep.py`(쓰러짐) · `scripts/fire_rule_search.py`(방화).

### 4.2 실패 원인을 먼저 가른다

규칙을 훑기 전에 **못 맞히는 편이 검출 실패인지 판정 실패인지** 갈라야 한다. 시계열 덤프로 본다.

```
C00_216_0003  정답창 부근 불 0.063 / 연기 0.000   -> 아예 못 본다. 데이터 문제. 규칙으로 못 푼다
C00_195_0001  정답창 부근 불 0.676 / 연기 0.964   -> 잘 본다. 규칙 문제
```

이걸 안 하면 규칙을 아무리 훑어도 안 풀리는 편에 시간을 쓴다.

**사람 항목에서는 반드시 (a) 구역 안으로 제한하고 (b) 창 전체를 세야 한다.** 2026-09-16 에 둘 다 틀렸다.

- 프레임 한 장(GT+2)만 보고 신뢰도 0.000 이라 "사람을 아예 못 본다" 고 했다.
  창 전체를 보니 같은 편에서 0.83~0.90 이 나왔다. 한 장은 우연이다.
- 그 0.83 은 **구역 밖 다른 사람**이었다. 구역으로 제한하니 다시 0 이었다.
  결론은 같았지만 근거가 틀렸다. 근거가 틀리면 다음 판단이 틀어진다.

세는 단위는 "구역 안 검출 표본 수 / 창의 표본 수" 다. 판정이 요구하는 체류를 채울 수 있는지가 바로 보인다.

```
침입 C00_249_0003   0/71   최고 0.000   필요 체류 2      -> 검출 실패
배회 C00_115_0001   3/71   최고 0.684   필요 체류 6.0초  -> 검출은 되지만 체류를 못 채움
대조 배회 C00_001_0001  59/71 연속       필요 체류 6.0초  -> 정상
```

도구: `scripts/fail_probe3.py` 식으로 제출 경로(`PersonDetector` · `entered`)를 그대로 부른다.

### 4.3 SA 시각 = onset + delay

KISA 는 알람 시각을 `onset + 10초` 로 적는다(`score_kisa.py` 의 `DELAY`).
**이른 onset 은 오히려 유효창 안에 들어온다.** 2026-09-15 에 이걸 잊고 "일찍 터져서 틀렸다"고
진단했다가 실제로는 "늦게 터져서 틀린" 것이었음을 나중에 알았다. 규칙별 onset 을 직접 찍어 확인한다.

### 4.4 응답면을 그린다. 한 점만 보지 않는다

최고값 하나만 보면 그게 봉우리인지 우연인지 모른다. 축을 훑어 **표로 찍는다.**

```
쓰러짐 (need 4 고정, 문턱 0.01 간격)
  0.15~0.69 -> 90.00    아래 벽: 가짜 신호가 여기서 넘는다
  0.70~0.81 -> 100.00   통로. 폭 0.11
  0.82~0.95 -> 94.74    위 벽: 가장 약한 진짜 낙상을 놓치기 시작
```

- **통로가 있으면 가운데를 고른다.** 벽에 붙은 값은 다른 영상에서 넘어간다.
- **통로 없이 한 점만 튀면 과적합이다.** 방화 신규칙 스윕의 `f0.14 2회/3스텝`(94.74)이 그 예다.
  문턱 0.14 는 거의 아무 데나 터지는 값인데 그 10편에서만 우연히 오검 0 이었다.
- **동점 개수가 과적합 지표다.** 540조합 중 20개가 동점이면 그 20개 중 무엇을 고르든
  이 10편에서는 같고 시험장에서는 다 다르다.

### 4.5 고른 규칙은 반드시 두 번 검증한다

같은 채점셋으로 고르고 그 채점셋으로 보고하면 낙관이 섞인다. 둘 중 하나는 해야 한다.

**(a) LOOCV** 한 편씩 빼고 나머지로 고른 뒤 뺀 편을 맞히는지 본다.

```
쓰러짐  전수 100.00  LOOCV 90.00  낙관 +10.00
```

낙관이 크면 "변별하는 편이 몇 개인가"를 본다. 쓰러짐은 9편이 문턱과 무관하게 맞고
한 편만 변별했다. 그 편을 빼면 60개 설정이 동점이 되어 고를 근거가 사라진다.
**즉 그 규칙의 근거는 1편이다.** 이건 LOOCV 숫자보다 중요한 정보다.

**(b) 다른 모델의 덤프에 대본다** — 표본이 적을 때 LOOCV 보다 강한 검증이다.

```
방화 신규칙을 학습 모델 44개 덤프(클립 평가 440건)에 적용
  기존 4/6   정검 250 미검 190 오검 50 · F1 평균 66.90
  신규 3/10  정검 268 미검 172 오검 44 · F1 평균 70.63
```

규칙이 **여러 모델에서 같은 방향으로** 좋아지면 그 모델 하나에 맞춘 것이 아니다.
이길 때 어디서 이기는지도 본다. 제출 후보(상위 mAP) 쪽에서 이기는 것이 의미 있다.

### 4.6 기전을 말로 설명할 수 있어야 한다

수치가 좋아도 왜 좋아지는지 못 말하면 채택하지 않는다.

- 쓰러짐 0.269 -> 0.755: 0.269 는 확신 없는 초기 신호에도 터진다.
- 방화 4회/6스텝 -> 3회/10스텝: 진짜 화재는 연기에 가려 검출이 띄엄띄엄 뜬다. 3초 안에 4번을 못 채운다.
- 방화에서 연기를 뺀 이유: 안개편은 연기가 0초부터 420표본 중 419회 0.6 을 넘고 기준선이 0.972 다.

### 4.7 다수 사건에서 "마지막 사람" 고르기

KISA 는 같은 사건에 사람이 여럿이면 **마지막 사람** 기준으로 알람 시각을 적는다.
그런데 배포 검증영상 30편을 세어 보면 **정답이 첫 배회자인 편이 26/28** 이다.
"마지막 사람" 을 글자 그대로 따르면 오히려 나빠진다(93.10 -> 89.66). 왜냐하면
뒤에 오는 사람들은 대개 그 사건과 무관한 행인이고 KISA 는 연출된 연기자만 표시하기 때문이다.

그래서 "언제까지를 같은 사건으로 볼 것인가" 가 규칙의 본체가 된다.
지금까지는 확정 대기(settle 5초) 하나로 잘랐는데, 두 사람이 13.5초 간격으로 들어오는
C00_211_0002 에서 첫 사람에 잠겼다(SA 114.5, 정답 128.0).

**한 축만 늘리면 반드시 다른 편이 깨진다.** settle 을 키우면 사람이 계속 드나드는 편에서 끝없이 밀린다.

| settle | 5.0 | 8.0 | 10.0 | 12.0 | 15.0 | 20.0 |
|---|---|---|---|---|---|---|
| 점수 | 93.10 | 86.21 | 82.76 | 68.97 | 65.52 | 58.62 |

450조합 격자(conf·dwell·settle·gap)의 최고도 93.10 이었다. **상수로는 못 푼다는 뜻이다.**
이럴 때는 새 축을 찾아야 하는데, 축 하나로도 안 된다. 실제로 하나씩은 전부 실패했다.

| 정책 | 점수 | 깨지는 편 |
|---|---|---|
| 지금(settle 5) | 93.10 | 211(두 사람 13.5초 차) |
| 첫 배회자 고정 | 89.66 | 211 · 232 |
| 동시재실이면 갈아탐 | 86.21 | 010 · 031 · 039_0002 |
| 동시재실 + 간격 상한 | 89.66 | 031 · 039_0002 |
| + 트랙 밀도 | 93.10 | 039_0002 |
| + 혼잡도 | 93.10 | 031 |
| **네 조건 동시** | **96.55** | 없음(오검 0) |

채택한 규칙: settle 안에 오면 그대로 받고, 늦게 와도 **아래 넷을 모두** 만족하면 받는다.

| 조건 | 뜻 | 이게 없으면 |
|---|---|---|
| `still_in` | 지금 고른 사람이 아직 구역 안 | 사건이 끝난 뒤 온 사람을 쫓는다 |
| `maxgap` 20초 | 너무 늦지 않았다 | 끝없이 밀린다 |
| `crowd` 3명 이하 | 그때 구역이 한산하다 | 붐비는 편(039_0002)에서 행인을 쫓는다 |
| 방금 도착 | 진입시각 == 그 트랙의 최초 구역 진입 | 검출이 끊겨 진입이 재계산된 옛 사람(031_0001)을 새 사람으로 센다 |

결과: 30편 93.10 -> **96.55(정검 28 미검 2 오검 0)** · LOOCV 89.66 -> **96.55(낙관 0.00)** ·
75조합 중 24개 동점(넓은 평지). 라이브 확인 `C00_211_0002 → SA 00:02:08`(GT 128, 정확히 일치),
나머지 편의 SA 는 한 초도 안 바뀌었다.

**배운 것**: 상수를 훑어도 최고가 지금 값이면 그건 "지금이 최적" 이 아니라 "축이 모자라다" 는 신호다.
그리고 새 축은 반드시 **말로 설명되는 것**이어야 한다(4.6). 위 넷은 전부 "같은 사건의 일행인가" 를
다른 각도에서 묻는 것이고, 그래서 LOOCV 낙관이 0 이 나왔다.

### 4.8 규칙으로 못 넘는 천장은 가중치를 겹쳐 넘는다

가중치를 고정한 채 규칙만 훑다 보면 "최고가 지금 값" 인 지점에 닿는다. 4.7 에서는 축이 모자란 경우였는데,
방화는 축이 아니라 **입력이 모자란** 경우였다.

배포 가중치 하나로 불문턱 9 x 창 9 x 횟수 5 = 315조합을 전수로 훑어도 **88.89 가 천장**이었다.
놓치는 두 편에서 모델이 아예 아무것도 못 보기 때문이다. 규칙은 못 본 것을 만들어내지 못한다.

그런데 44개 학습 구성의 덤프를 전부 훑으니 **두 편을 각각 잡는 구성이 따로** 있었다.

| 가중치 | 학습 | 잡는 편 | 못 잡는 편 |
|---|---|---|---|
| fresh_48k_wildall @640 | 안개 네거티브 포함 | 안개편 C00_195_0001 | 눈편 |
| s2_s960 @960 | 960 학습(작은 객체) | 눈편 C00_216_0003(25x12px 불씨) | 안개편 |

6뷰 타일에 두 모델을 다 태우고 표본마다 최고 신뢰도를 쓰면 둘 다 잡는다.
**88.89 -> 100.00 (라이브 실측).** 추론 비용은 2배다.

우연이 아니라 기전이 설명된다(4.6). 안개로 학습한 모델이 안개편을, 고해상도로 학습한 모델이 작은 불씨를 본다.

**다만 규칙은 여전히 과적합할 수 있다.** 100 이 나오는 규칙이 여럿이었는데 대부분 쓰면 안 되는 것이었다.

| 규칙 | 10편 | 44개 단일 덤프 오검 | 44개 평균 |
|---|---|---|---|
| 지금 불0.45 창10 3회 | 88.89 | 44건 | 70.63 |
| 불0.15 창8 3회 | 100.00 | **89건** | 65.77 |
| 불0.20 창8 2회 | 100.00 | **100건** | 63.73 |
| **채택 불0.40 창20 3회** | 100.00 | **42건** | **72.74** |

**고른 규칙을 여러 모델 덤프에 걸어 오검이 늘지 않는지 본다.** 10편에서만 100 이면 버린다.

### 4.9 덤프로 고른 규칙이 라이브에서 안 맞을 때

오늘 방화가 84.21 -> 90.00 -> 100.00 으로 움직였다. 규칙은 한 번도 안 바꿨다. **입력 경로가 달랐다.**

**(a) 덤프를 만든 가중치가 사라져 있었다**

`runs/s2_s960_20260913` 이 재학습 실패로 덮어써져 있었다(status train_failed, epoch 3, 클래스 이름조차 없음).
좋은 덤프는 09-14 파일로 남아 있는데 그 모델은 09-15 에 사라진 것이다. 그걸 앙상블에 넣으니 라이브에서
불 신뢰도가 전 구간 0.000 이었다.

    덤프는 파일로 남고 가중치는 재학습에 덮어써진다. 덤프만 보고 모델을 고르면 안 된다.

`scripts/fire_weight_check.py` 로 편마다 상위 3표본을 다시 재 본다. 같으면 그 가중치가 그 덤프를 만든 것이다.
(원본은 `logs/_archive/` 에 있었다. 지우지 않고 옮겨 둔 덕분에 살았다.)

**(b) 배치 추론과 낱장 추론이 다르다**

덤프를 만든 `score_kisa.py` 는 타일을 하나씩 넣고, 제출 경로는 6장을 한 배치로 넣고 있었다.
울트라리틱스는 배치에 크기가 다른 이미지가 섞이면 공통 크기로 패딩하므로 타일마다 실효 배율이 달라진다.

    같은 프레임 · 같은 가중치   배치 0.545  /  낱장 0.519

차이는 작지만 문턱 근처에서 판정을 뒤집는다. 실제로 안개편이 이것 하나로 갈렸다.

    낱장(덤프와 동일)  113.5초 0.519 · 122.0초 0.514 · 123.0초 0.477 -> 3회 충족 -> SA 123.5  정검(여유 0.5초)
    배치               세 번째가 문턱 아래 -> 나중에 터짐        -> SA 132.0  오검

**규칙을 덤프로 고르면 라이브도 덤프와 같은 방식으로 추론해야 한다.** 고친 뒤 라이브가 덤프와 소수점까지 같아졌다.

**교훈**: 라이브와 오프라인이 어긋나면 규칙부터 의심하지 말고 **입력을 표본별로 맞대라.**
어느 표본에서 갈리는지 보면 원인이 바로 나온다(가중치인지 전처리인지).

### 4.10 보고할 때

- **고정 규칙 점수를 대표값으로 쓴다.** 스윕 최고값은 "규칙을 잘 고르면 여기까지 가능하다"는 상한이다.
- 스윕값을 적을 때는 전수·LOOCV·동점 개수를 같이 적는다.
- 측정 방식을 바꾸면 그 전후 수치는 **비교 불가**라고 명시한다(2026-09-14 사람 항목 채점 경로 교체가 그 예).

### 4.11 규칙으로 못 고치는 미검을 가려내는 법

2026-09-16, 침입 미검 3편(94.74 의 나머지).
규칙을 더 만지기 전에 **덤프가 애초에 무엇을 담고 있는지**부터 봤다. 네 단계로 가른다.

1. 사람이 검출됐나 (박스 0개?)
2. 검출됐는데 구역 밖인가 (`entered` 통과?)
3. 구역 안인데 신뢰도가 낮나 (`conf` 문턱?)
4. 다 넘었는데 연속이 안 되나 (`hold` 표본?)

세 편 다 **3번에서 걸렸다.** 구역 안 박스의 최고 신뢰도가 0.19 / 0.18 / 0.41 이고 문턱은 0.45 다.
`sa=None` 은 "마지막 사람을 잘못 골랐다" 가 아니라 "아무도 진입으로 안 잡혔다" 는 뜻이다.
그래서 4.7(다수 사건에서 마지막 사람) 계열 규칙으로는 못 고친다.

| 클립 | 장면 | 구역 안 사람 크기 | 최고 신뢰도 | 성격 |
| :-- | :-- | --: | --: | :-- |
| C00_249_0003 | 주간 설경, 울타리 뒤 | 22~36px | 0.19 | 원경 소형 |
| C00_275_0001 | 야간 안개, 담장 위 | 17~36px | 0.41 | 원경 소형 + 저대비 |
| C00_255_0001 | 야간 IR, 벽면 근접 | **279~327px** | 0.18 | **크기 문제가 아니다** |

C00_255_0001 은 눈으로 보면 사람이 또렷하다. 그런데 박스 238개 중 **210개의 `y1` 이 정확히 432** 다.
432 는 3x3 타일의 아래 줄 시작 y 다. 타일 경계에 눌린 거대 박스가 클립을 지배하고 있었다.
정상 편(C00_005_0001)은 181개 중 11개뿐이다.

타일 구조를 의심해 GT 시각 프레임의 9개 타일을 하나씩 다시 돌렸다.
사람이 통째로 들어 있는 가운데-왼쪽 타일(y 192~528)이 **conf 0.05 에서도 0개**였다.
가중치와 해상도를 바꿔도 마찬가지였다.

```
person_v3  전체프레임 640   1개 [0.18]     person_v2  전체프레임 640   0개
person_v3  전체프레임 1280  0개            person_v2  전체프레임 1280  0개
person_v3  가운데타일 960   0개            person_v2  가운데타일 960   1개 [0.15]
person_v3  가운데타일 1280  0개            person_v2  가운데타일 1280  2개 [0.11, 0.08]
```

**타일 문제도, 해상도 문제도 아니다. 야간 IR 장면을 두 가중치 모두 못 본다.** 학습 데이터 쪽 문제다.

#### 문턱을 낮추면 되는가: 안 된다

덤프 30편에 `conf` x `hold` x `corners` 를 전수로 걸었다(`scripts/conf_sweep.py`).

| conf | hold 2 · corners 3 | 미검 3편 SA (GT 111 / 137 / 134) |
| --: | --: | :-- |
| 0.45 | **94.74** | - - - |
| 0.40 | 94.74 | - - - |
| 0.35 | 91.23 | - - - |
| 0.30 | 89.66 | - - 33 |
| 0.20 | 79.31 | - - 49 |
| 0.10 | 75.86 | - - 68 |

- 지금 값은 **고원 위**에 있다(0.45 와 0.40 이 같다). 한 점만 보고 고른 값이 아니다.
- 세 편은 **어떤 설정에서도 창 안으로 안 들어온다.** C00_275_0001 이 터지는 33·49·68초는 GT 134 와 100초 넘게 어긋나 오검+미검으로 두 번 깎인다.
- `hold` 1 (70.18) 도 `corners` 1 (84.21) 도 전부 나쁘다. 지금 조합이 격자 안에서 최고다.

#### 배운 것

- **미검을 보면 규칙부터 만지지 말고 덤프의 네 단계를 먼저 가른다.** 3번(신뢰도)에서 걸리면 규칙으로 못 고친다.
- `y1` 같은 좌표가 한 값에 몰리면 타일 경계 의심. 다만 이번엔 원인이 아니라 증상이었다.
- 문턱을 낮춰 미검을 살리려 할 때는 **그 편이 창 안에 들어오는지**까지 본다. 창 밖에서 터지면 두 번 깎여 더 나쁘다.

### 4.12 "더 일찍 잡는 것" 이 감점인 채점 구조

2026-09-16. "옅은 연기는 라벨에서 빼고 알고리즘으로 잡자" 는 제안을 덤프로 검증했다.

**라벨 쪽 지적은 맞다.** 지금 연기 채널이 이미 그 증상이다. 영상 앞 60초 연기 신뢰도 기준선:

```
C00_195_0001  0.972   <- 안개편. 불나기 전부터 연기가 0.97
C00_089_0001  0.743   <- 연무
나머지 8편     0.000
```

연기 조건을 켜면 88.89 -> 63.16, 오검 44 -> 73~103. 그래서 `smoke=1.1` 로 껐다.

**그런데 알고리즘으로 옮겨도 KISA 점수는 못 올린다.** 채점 창이 `[GT-2초, GT+10초]` 라
**GT 보다 일찍 터지면 정검이 아니라 오검 + 미검으로 두 번 깎인다.**

| 판정 방식 | 최고 점수 | 실패 모양 |
| :-- | --: | :-- |
| 연기 절대 문턱 (0.3~0.8 훑음) | 11.11 | 미검 9~10 · 오검 3~8 |
| 연기 기준선 대비 상승 (`rule="new"`) | 12.50 | 같음 |

안개편 때문만이 아니다. 기준선 0.000 인 맑은 편에서도 연기가 GT 보다 먼저 올라간다.

```
C00_049_0001  GT 207   GT 이전 연기 최고 0.659
C00_146_0003  GT 124   GT 이전 연기 최고 0.885
C00_272_0003  GT 123   GT 이전 연기 최고 0.889
```

연기를 잘 잡을수록 SA 가 GT 앞으로 당겨져 창을 벗어난다.
**연기 성능 향상이 이 채점에서는 마이너스다.** (`scripts/smoke_look.py`, `scripts/smoke_rel.py`)

지금 규칙에 기준선 연기를 더해도 100.00 그대로다(2편의 SA 만 바뀌고 판정은 안 바뀐다).
얻는 것 없이 변수만 는다.

#### 배운 것

- **"조기 검출" 과 "정시 검출" 은 다른 목표다.** 실사용 조기 경보에는 옅은 연기가 가치 있지만
  KISA 창 채점에서는 감점이다. 두 목표를 한 파이프라인에 섞지 않는다.
- 새 신호를 넣기 전에 **그 신호가 GT 보다 먼저 올라가는지**부터 본다. 먼저 올라가면 규칙으로 못 늦춘다.
- 시계열 모델이 방화에 "필수" 는 아니다. 프레임 단위 불 검출 + 세는 창으로 10편 100.00 이다.
  쓰러짐은 SeqNet 없이는 안 됐지만(4.x) 방화는 됐다. 항목마다 다르다.
- 옅은 연기 라벨은 **버리지 말고 따로 뺀다.** 나중에 시계열 모델을 붙일 때
  클립 단위 약한 라벨(GT 시각)로 쓸 수 있다. 새 bbox 라벨 없이 시작할 수 있다.

## 5. 잡이 죽을 때 계측 거는 법

2026-09-15 에 `rc=-9` 로 다섯 번 죽는 동안 가설만 바꿔 가며 헤맸다.
**계측을 먼저 걸었으면 한 번에 잡았다.**

### 5.1 rc 값이 무엇을 말하는가

| rc | 뜻 | 어디를 보나 |
|---|---|---|
| `-9` | SIGKILL. **밖에서 죽인 것** | OOM 킬러, 고아 정리, 사람이 kill |
| `1` + 파이썬 트레이스백 | 코드가 던진 예외 | CUDA OOM 도 여기다 |

**GPU 가 모자라면 파이썬 예외가 나지 SIGKILL 이 안 난다.** `rc=-9` 를 보고 GPU 를 의심하면 헛짚는다.

### 5.2 계측기는 저장소 안에 둔다

`scripts/memwatch.sh` 를 `bash scripts/memwatch.sh` 로 돌린다. 3초마다 남긴다.

**`/tmp` 에 두면 안 된다.** noexec 라 실행이 막힌다(`Permission denied`). 게다가 `/tmp` 은
tmpfs(RAM)라 거기 쓴 파일이 그대로 메모리를 먹는다. 임시 산출물도 `/NHNHOME`(NVMe)에 둔다.

### 5.3 읽을 때 조심할 것

**`free` 의 `shared` 와 `df /dev/shm` 은 다르다.** 파이토치 데이터로더는 공유메모리 파일을 만들고
바로 `unlink` 한다. `df` 에는 안 보이지만 그 100GB tmpfs 를 실제로 쓴다.

```
free -g        shared 61G     <- 실제 사용량
df /dev/shm    720K           <- unlink 된 것은 안 보인다
```

큰 데이터셋(20만장 이상) 두 개를 동시에 띄우면 이 한계를 넘긴다. 워커 수를 줄이는 것이 직접적인 해법이다.

**`nvidia-smi` 는 컨테이너 안에서 호스트 PID 를 보여준다.** `ps -p <pid>` 로 안 잡힌다고
남의 컨테이너라고 단정하면 안 된다. 우리 것일 수 있다. 확인은 이렇게 한다.

```bash
for d in /proc/[0-9]*; do
  ls -l $d/fd 2>/dev/null | grep -q nvidia && { echo -n "${d#/proc/} "; tr '\0' ' ' < $d/cmdline; echo; }
done
```

### 5.4 고아 데이터로더 워커

학습이 SIGKILL 로 죽으면 워커들이 `PPid 1` 고아로 남아 **RAM·공유메모리·GPU 를 계속 쥔다.**
2026-09-15 실측으로 GPU 126.6GB · RAM 123GB · 공유메모리 89GB 를 죽은 잡의 워커가 붙잡고 있었다.
그 상태로 다음 잡을 띄우면 모자라서 또 죽고 고아가 더 쌓인다. 다섯 번 죽은 것이 이 고리였다.

- 러너가 **학습 실패 직후** `kill_orphan_trainers()` 를 부른다(`scripts/exp_queue.py`).
  예전에는 러너가 새로 뜰 때만 돌아서 실패가 이어지면 계속 쌓였다.
- 손으로 치울 때 패턴을 빠뜨리지 않는다. `model.py train` 만 잡으면 **`resume_train.py` 워커를 놓친다.**

```bash
pkill -9 -f 'model.py trai[n]'      # 대괄호 트릭: 이 명령 자신이 안 잡히게
pkill -9 -f 'resume_train.p[y]'
```

- 치운 뒤 GPU·`shared` 가 떨어지는지 본다. 떨어지면 그게 원인이었다.
